# Arcaea 拆谱器 —— 原理与权重详解

拆谱器读入一份 `.aff` 谱面，给**每个判定物件**（tap / hold / arctap）算出一个
左右手标记，输出一份只多了这个标记的副本。

它为什么能用：谱面是斜视的 3D 平面，**横竖两个方向的尺度不一样**
（横向 1 个坐标单位比纵向 1 个单位长 1.64 倍），
所以"这只手来不来得及"不能用横向坐标拍脑袋，得按真实几何长度算；
而"该不该拆成左右交替"这件事，本质上是**一帧一帧地比代价**。下面全部围绕这两点。

什么人可以用: 
- 帮助拆分官谱/自制谱, 虽然准确度不可能达到100%, 但至少有90%以上, 可以大大减少手动拆分工作量
- 开发ai制谱的人, 可以利用此程序审查谱面中出张/手速是否有过于不合理/过于轻松的情况, 一定程度上量化谱面信息.
- 发挥你的想象力吧

## 0. 怎么调用

```bash
# 拆一份谱面（默认输出 <名>.splited.aff）
python3 spliter_aff.py 谱面.aff

# 指定输出 + 质量报告
python3 spliter_aff.py 谱面.aff -o out.aff --stats

# 逐键看"为什么给它这只手"
python3 spliter_aff.py 谱面.aff --explain 20

# 看音弧颜色产生的硬约束
python3 spliter_aff.py 谱面.aff --show-constraints

# 调两个权重（只有这两个）
python3 spliter_aff.py 谱面.aff --jack 5 --move 1.2
```

安装后也可以直接 `spliter 谱面.aff`。纯 Python 标准库，Python ≥ 3.10。

| 开关 | 含义 |
| --- | --- |
| `input` / `-o, --out` | 输入 `.aff` / 输出路径（默认 `<名>.splited.aff`） |
| `--jack W` | ★ 抗（同手连打）权重，默认 `4.0`, 越大越倾向于拆 |
| `--move W` | ★ 移动/速度权重，默认 `1.0` ,越大越倾向于抗|
| `--stdout` / `-f, --force` | 结果打到标准输出 / 允许覆盖已存在的输出 |
| `--stats` | 拆前拆后对比、位移速度榜、手速榜、警告 |
| `--explain [N]` | 逐键依据（默认 40，`0` = 全部） |
| `--show-constraints` | 音弧颜色产生的硬约束 |
| `--json` / `-q` / `--version` | 机器可读结果 / 安静 / 版本 |

**手标记是 `0`（左手）/ `1`（右手）**，写在括号内末尾。
`arc(...)` 的第 8 个参数 `color` **本来就是它的手标记**，所以 `arc` 一个参数都不改：

```
(23720,2);                ->  (23720,2,1);           # tap：末尾补
hold(34883,35232,3);      ->  hold(34883,35232,3,0); # hold：末尾补
arc(...)[arctap(23720)];  ->  arc(...)[arctap(23720,0),arctap(24593,1)];
                                                     # arctap：括号内补，arc 参数不动
arc(...,1,none,true);     ->  arc(...,1,none,true);  # arc 自身：完全不动
```

已经标过的行会**原位替换**，所以对同一份文件重复处理是幂等的。

注意: 这套标记是对应arcade_alpha的格式，官谱原生不支持，其他制谱器请自行寻找。

## 1. 拆谱在解什么问题

"拆谱"就是决定**每个键用哪只手按**。程序把它当成序列决策 + 全局权衡：

```
按时间顺序扫过所有物件
  每个物件选一只手 → 累计代价
  代价 = 移动 + 抗 + 硬度 + 空间 + 换手 + 反手 + 占手 + 均衡
  硬约束 = 原生标记 / 音弧颜色 / 一键一手 / 长条尾指同手
求解 = 束搜索 → 局部优化（翻转 / 交换 / 前缀翻转 / 镜像）
```

核心难点是"**抗**与**拆**的边界在哪"。这套实现的答案是**不拍密度阈值**，
而是把它拆成几个各自有物理含义的可调项，让它们互相制衡：

| 现象 | 由什么决定 | 主要参数 |
| --- | --- | --- |
| 单手来不及了，必须换手 | 位移速度超过舒适值 | `physics.comfy_speed` / `max_speed` |
| 手跑得动，但"一根手指连点"很难受 | 时间间隔太短（不看位置） | `cost.hardness` / `hardness_window` |
| 同一只手挪一点点再按（真"抗"） | 距离 + 间隔 | `cost.jack` / `jack_min_distance` |
| 明明一只手能顺下来，却每下都换手 | 换手次数 | `cost.switch` |
| 两只手交错着按得很挤 | 反手 + 真实距离 | `cost.cross` / `cross_hand` |

### 时间怎么读：毫秒 ↔ BPM × 节奏

本文档里所有时间门槛都用**毫秒**写（那是程序的单位），但**第一次出现时都会附上
"对应多少 BPM 的几分音符"**，因为玩家是那么想问题的。

换算就是标准的 `间隔 = 60000 / BPM × (4 / 音符数)`。本文档全篇以
**172 BPM** 为锚点 —— 这是参考谱面的速度，也是标定 `jack_window` 时用的基准：

```
172 BPM：4分 = 349ms    8分 = 174ms    16分 = 87ms
```

**约定**：凡是对应"**拆**"（交替、交互、换手）的说法，优先用 **16 分**举例；
凡是对应"**抗**"（同手连打、长条占手）的说法，优先用 **8 分**举例。
个别数值用这两种音符都会掉出合理 BPM 区间时会另外注明（见 §3.2 的 50ms）。

几个直觉例子（都能用 `--explain` 复现）。

> **距离一律按"轨道"讲**：**1 轨道 = 相邻轨道的间距 = 0.5 个谱面坐标**。
> 像素随设备分辨率变化、玩家也毫无体感，而轨道数是谱面上能直接数的。
> 纵向位移不属于"轨道"这个概念（轨道是横向的），直接用坐标高度讲
> ——`y=0` 是判定线、`y=1` 是满高。

```
250ms 内横移 1 轨道（0.5 坐标）   → 一只手扫完（120BPM 8分）
125ms 内横移 1 轨道（0.5 坐标）   → 仍然一只手（120BPM 16分）
87ms  内横移 2 轨道（1.0 坐标）   → 必须交互（172BPM 16分）
同键位 250ms 连按                 → 交给一只手（120BPM 8分；不罚，人也是这么打的）
```

换算参考（`--stats` 里"位移速度"的"轨道/秒"就是这个尺度）：

| 横移 | 坐标差 | 体感 |
| --- | --- | --- |
| 1 轨道 | 0.5 | 相邻轨，最常规的换位 |
| 2 轨道 | 1.0 | 跨半个判定面 |
| 4 轨道 | 2.0 | 从最左到最右（1 轨 ~ 4 轨） |
| 满高 | `y` 差 1.0 | 地面 ↔ 天顶，约等于 1.22 轨道 |

**注意区分两个东西** —— 它们都容易被叫成"手速"，但完全是两回事：

| | 问的问题 | 口径 | `--stats` 里的名字 |
| --- | --- | --- | --- |
| **位移速度** | 这只手**要跑多远**？ | 位移 ÷ 可用时间（轨道/秒） | "最吃位移速度的几处" |
| **手速榜** | 这个手指**多久要再落一次**？ | 同手相邻两键的时间间隔（ms） | "手速榜" |

手速榜只看 **tap / arctap / hold 头**（音弧不是"落一次"；hold 用**头**的时间），
**与位移完全无关**。间隔会顺带说成节奏单位：

```
第一名, 间隔 87ms, 相当于 BPM 172 的 16 分音符, 99069-99156等 27 组
```

换算规则：先按 **8 分**（`间隔 = 30000 / BPM`）；等效 BPM 超过 300 就改说
**16 分**（`间隔 = 15000 / BPM`），**再快也只说到 16 分**。同一间隔并列的
只举一对例子，但会报出总组数。

**位置一律用"时刻"（ms）表示**，两个榜都是 —— 行号只在编辑器里有意义，
玩家是按时间找位置的。上面的 `99069-99156` 就是"从 99069ms 到 99156ms"。

谱面里常见的 **1ms 错位和弦**（例如 53051 的 arctap 配 53052 的 hold）算**一个和弦**，
不是"再落一次"也不是"一次移动"，所以**不进这两个榜**。判据是项目统一的
`SAME_HAND_MARGIN_MS`（相差 ≤ 2ms 视为同一时刻）。

`--stats` 最后的"需要注意"里，凡是能定位的问题都会**列出具体位置**
（例如"长条还没松手就要按下一个键"会给出长条区间、那个键的时刻、以及重叠了多少），
最多列 5 处，其余的折成"还有 N 处未列出"。

## 2. 两个坐标系：这是最容易错的地方

### 2.1 轨道坐标

**每条轨道宽 0.5 个单位**，4 条轨道共 5 条边界 `-0.5 / 0 / 0.5 / 1.0 / 1.5`，
而 tap/hold 落在轨道**中点**：

```
x = -0.25 + (lane - 1) * 0.5
```

| 轨道 | 跨的区间 | 中点 x |
| --- | --- | --- |
| lane 1 | `[-0.5, 0.0]` | `-0.25` |
| lane 2 | `[ 0.0, 0.5]` | ` 0.25` |
| lane 3 | `[ 0.5, 1.0]` | ` 0.75` |
| lane 4 | `[ 1.0, 1.5]` | ` 1.25` |

### 2.2 横竖尺度不同：为什么位移不能只看 x

判定面是**斜视的 3D 平面**，横向 1 个坐标单位在屏幕上比纵向 1 个单位**长**：

| 方向 | 屏幕长度 | 依据（游戏内截图实测） |
| --- | --- | --- |
| 横向 | 1 单位 = **1.64 个满高** | lane1 中点(−0.25) ~ lane4 中点(1.25) = 1.5 单位 ≈ 804px |
| 纵向 | 1 单位 = **1 个满高** | y = 0（判定线）~ y = 1（天顶）= 326px |

所以任何位移都要分轴合成；**只看 x 会把"同一横坐标、从天到地"的位移
（整整 1 个满高）当成 0**。

换成轨道口径记住三个数就够了：

- **1 轨道**（相邻轨道间距 = 0.5 单位）= **0.82 个满高**的长度；
- 满高（纵移 1.0）= **1.22 轨道**；
- 整块判定面**横着正好 4 个轨道宽**（1 轨 ~ 4 轨 = 2.0 单位），
  纵向上就是 1 个满高。

> 代码里保留了两个轴的像素刻度（`536` / `326` px/单位）作为**标定基准**：
> `neutral_band` / `strong_bias` / `max_reach` / `jack_min_distance` 这些参数
> 都是按像素写的，用之前必须除以刻度换算到坐标，否则会出现
> "15 像素的中性带变成 15 个世界单位"那类错配。
> 但这些数字**只在代码与标定处出现**，给人看的报告与文档一律用轨道。

**Arctap 没有自己的坐标**：它只带一个时间戳，位置由所属音弧按缓动曲线插值算出
（`siso` 这类组合缓动表示 X 轴用前两个字母、Y 轴用后两个字母）。

## 3. 时间类权重

时间类的项都用**连续收尾**（`_taper_factor`）而不是硬截断：**100ms 以内
（150 BPM 的16分）**原样，之后线性收到 0。硬截断会让 99ms 和 101ms 的分法
天差地别，而人的手感是连续的。

### 3.1 移动 `move` —— 唯一可调的两个旋钮之一

**只看速度，不看距离。** 手完全可以在两拍之间慢慢挪很远。

```
move_cost(i→j, 手):
    dt = t_j − t_i
    dt ≤ 0（同一时刻）            → 0     （手是"已经就位"的两个落点）
    起点/时间要扣掉按住的时间      → 见 §5
    Δ    = 位移长度（横向按轨道、纵向按满高，分轴合成）
    speed = Δ / 可用时间
    ratio = speed / comfy_speed          comfy_speed ≈ 11.6 轨道/秒

    move × ratio^0.3 × (低于舒适线打五折) × arrival
    speed > max_speed（≈35 轨道/秒）再加 40·(ratio−1)²
    单次封顶 40
```

实测的代价曲面（`cost.move = 1`），列头是该间隔对应的节奏：

| 横移 \ dt | 87ms<br>172BPM 16分 | 174ms<br>172BPM 8分 | 250ms<br>120BPM 8分 | 500ms<br>120BPM 4分 |
| --- | --- | --- | --- | --- |
| 0.5 轨道 | 0.405 | 0.329 | 0.295 | 0.239 |
| 1 轨道 | 0.498 | 0.405 | 0.363 | 0.295 |
| 2 轨道 | 1.226 | 0.498 | 0.447 | 0.363 |
| 4 轨道（横穿全屏） | 5.515 | 1.226 | 1.100 | 0.447 |

三点值得注意：

- **`move_speed_power = 0.3`，不是 2**。指数为 2 时"间隔减半就贵 4 倍"，
  密集串里"让手跑过去换手"被算得太贵，模型宁可插同手对。压平之后位移代价几乎与
  速度无关，但保留了远近差异。
- **速度低于舒适线只打五折，不是免费**。低于 `0.7×comfy` 完全不罚的"免费区"
  会造成系统性偏差 —— "为了交互而多跑的那几步"是免费的，模型于是偏向
  "一只手赖着不动"。
- **`arrival`（移动到音弧更轻）**：位移的终点如果要接住一条**实体弧的弧头**，
  这步乘 `arc_arrival = 0.35`。依据是音弧只有最高一级判定，赶去接它的到位要求
  比点类松。移动到 hold 暂不减轻。

### 3.2 抗 `jack` —— 唯一可调的两个旋钮之二

同一个手在 `jack_window = 150ms`（**200 BPM 的8分**）内连按两下。**越远越重。**

```
jack_cost(i→j, 手):
    dt > 150ms                     → 0
    d = 两键的真实屏幕距离
    死区 = jack_min_distance = 0.1 单位（= 1/5 轨道）

    d ≤ 死区:
        是 bullet（见下）           → jack × jack_time × 时间因子   （0.2 折价，轻松）
        不是 bullet（密集同键连按）  → spatial = 1，满额罚
    d > 死区:
        spatial = (d − 53.6) / (268 − 53.6)   线性，一个轨道宽处到达最重

    时间因子 = (150 − dt) / 150
    死区内再乘 (1 + 0.3 × 时间因子²)          小间隔额外加重
    速度超过 comfy_speed 时再加一份超速加成

    代价 = jack × (spatial + 超速 + (1−spatial)×jack_time)
              × 时间因子 × 收尾系数
```

实测（同手相邻两下，都是**同键位**）：

| 间隔 | 相当于 | 在密集流里（非孤立） | 孤立的两次（bullet） |
| --- | --- | --- | --- |
| 50ms | 150 BPM 的**32分** | **2.283** | 0.533 |
| 87ms | **172 BPM 的16分** | **0.782** | 0.336 |
| 90ms | 167 BPM 的16分 | 0.320 | 0.320 |
| 100ms | 150 BPM 的16分 | 0.267 | 0.267 |
| 120ms | 125 BPM 的16分 | 0 | 0 |
| 150ms | 200 BPM 的8分 | 0 | 0 |

**表里藏着一个结构**：50ms 和 87ms 这两行，密集流比孤立贵一倍以上；
但从 **90ms 起两列完全相同** —— 因为 ≥90ms 一律判为 bullet。
**分叉只发生在 90ms 以下的密集段**，这正是 `bullet` 判据的全部意义。

**"同键位连按"必须分成两种**，这是整套实现里最反直觉的一处：

- **bullet**：同位置（≤ 1/5 轨道）**且相对孤立**（前后 150ms = 200 BPM 8分 内没有别的键），
  或者间隔 ≥ 90ms（**167 BPM 的16分**；手指完全来得及再落一次）。原地弹一下，
  按 `jack_time = 0.2` 折价，很轻松。**孤立的同键连按不该被判成交互。**
- **密集流里的同键连按**：同一个动作，但"相对孤立"不成立 —— 这是硬抗里
  **最难受**的一种，满额罚。

`bullet_min_gap = 90ms` 就把这两者分开：**172 BPM 的16分（87ms）重罚，
167 BPM 的16分（90ms）已经是子弹。** 密集同键连按稳定拆成交互，
而孤立的 bullet 依旧轻罚，两者不再混为一谈。


> `jack_time` 取 0 会漏判：密集同键连按的强度落到 `(1−spatial)×jack_time`，
> 取 0 就意味着"一只手连点"免费，整串 16 分交互会被判成单手。

**150ms 这个窗口也是标定出来的**：收到 120ms（**125 BPM 的16分**）会让
125 BPM 那一档不再收抗，个别"为躲抗而反手出张"能解开，但更多地方
那个间隔的同手本来就该收抗 —— 合计变差，所以定在 150ms（200 BPM 的8分），
正好卡在 172 BPM 的16分（87ms）与 172 BPM 的8分（174ms）之间。

### 3.3 硬度 `hardness` —— 只看时间，不看位置

一根手指 150ms（**200 BPM 的8分**）内连点两下，和两根手指交替，难度不一样。
这是"高密度必须拆交互"的主要理由，和 `jack` 互补：

```
hardness_cost(i→j):
    dt > hardness_window = 200ms   → 0        # 200ms = 150 BPM 的8分
    代价 = hardness × (1 − dt/200) × 收尾系数
           hardness = 1.3
```

它**不看位置**，所以哪怕是同位置连按也照收（bullet 打个折）。
`jack` 管的是"挪一点点再按"，`hardness` 管的是"单指连点的频率上限"，
两者叠加才覆盖全部情况。

### 3.4 换手 `switch` —— 按整组记，且密集串里反过来奖励交替

同一时刻的几个键是**同时**按下去的，两只手都已经落在键上，谈不上
"从这只手换到那只手"。所以规则是：

- **多押不记**换手；
- 进入这一组多押时，只要上一组收尾的那只手这一组也在用，就算延续，不记；
- 离开这一组多押时若两只手都用过，则下一组用哪只都不算换手。

**按整组记很关键**：早期按扫描顺序逐键记，而组内顺序又按 x 排 —— 等于让
"哪个键在最左边"决定谁算入口/出口，凭空造出一笔与位置无关的偏好，
足以把一处很小的空间优势压过去、判成反的。

换手代价还**随间隔衰减**（`switch_window = 150ms` = 200 BPM 的8分，
与 `jack_window` 对齐），并且密集串里有一个**负代价**：

| 与上一组的间隔 | 相当于 | 换手代价 |
| --- | --- | --- |
| 50ms | 300 BPM 的16分 | **−0.233**（奖励） |
| 100ms | 150 BPM 的16分 | **−0.267**（奖励） |
| 130ms | 115 BPM 的16分 | **−0.287**（奖励最强） |
| 140ms | 107 BPM 的16分 | +0.007 |
| ≥150ms | 200 BPM 的8分 | 0 |

依据：参考谱在密集串里写的是**严格两手交替**（不看空间），而模型原来只在
"同手连打更贵"时才交替，相位/是否插入同手对就成了平局噪声。所以 ≤130ms
（**≥115 BPM 的16分**，也就是 172 BPM 谱面里的 16 分密集串）时，
换手不再收费、反而给一笔负数奖励严格交替。

> **窗口必须与 `jack_window` 对齐**：窗口比 jack 长的话会出现"jack 已经为 0、
> switch 还在收"的区间，那里唯一的偏好反而推着求解器去硬抗。

## 4. 空间类权重

### 4.1 静态归属 `home` —— "这个键在左半屏还是右半屏"

```
wrong = max(0, x − 0.5)  若给左手
      = max(0, 0.5 − x)  若给右手
若 wrong > 0:
    代价 = base × 0.25 × 3.0 × (wrong / 1.194) × 时长放大
    base = move × (物件宽 / 默认宽)
```

在 `center_x = 0.5` 处为 0，越往外侧越贵，**线性、无阈值**。实测：

| x | 给左手 | 给右手 |
| --- | --- | --- |
| −0.25（1 轨） | 0 | 0.471 |
| +0.25（2 轨） | 0 | 0.157 |
| +0.50（中线） | 0 | 0 |
| +0.75（3 轨） | 0.157 | 0 |
| +1.25（4 轨） | 0.471 | 0 |

长条在这一项上有**时长放大**（`1 + 占手时长/200`）：按住 400ms
（**75 BPM 的8分**）的长条 = 3 倍。
理由是长条按住的这段时间手一直被锁在错的一侧，比"单个键偏侧"严重得多。

**`home` 的取值有讲究。** 原值 0.06 太轻（偏侧 0.25 单位只罚 0.038，
比一次换手还小），会出现整段分法反过来；现在取 0.25。

### 4.2 同刻同 y 差一轨 `lane_reverse` —— "空间左右是硬道理"

两个键**同时开始、y 相同、x 相差正好一个轨道（0.45~0.55）**时，
反手要狠狠罚（权重 2.0）。实测这样一对键反手给左手的代价是 **2.307**，
是普通静态反手的十几倍。

用户口径是"这种一对键两手必须分开，于是空间上谁左谁右没有任何余地"。
判据收得很紧：差值 ≥ 1.0 时，哪怕其他条件都符合也不能用这条规则。

### 4.3 挤在一起时的反手 `cross`

相邻两键（不同时刻）若**左边那个给了右手 / 右边那个给了左手**（反手），
且真实距离落在 `cross_near = 0.2 轨道` ~ `cross_far = 1.0 轨道` 之间时加罚，
形状是**抛物线**（两端为 0、中点为峰值 `cross = 0.6`）：

| 距离 | 代价 |
| --- | --- |
| 0.12 轨道（≤ 0.2 轨道） | 0（太近，算同一个点 → 交给"抗"管） |
| 0.30 轨道 | 0.263 |
| 0.60 轨道 | **0.600**（峰值） |
| 0.90 轨道 | 0.263 |
| 1.20 轨道（≥ 1.0 轨道） | 0（太远，交错已经不挤） |

理由是**手指有宽度**：两键挤在一起时左右手交错比拉开距离更难受
（0.6 轨道处的反手比 2 轨道处更难打）。注意峰值落在**半轨到一轨之间** ——
比"相邻轨道"还近，也就是手指几乎叠在一起的时候最难受。

### 4.4 双手交叉 `cross_hand`

某个键分给某只手后，那只手落在**另一只手的另一侧**（左手在右、右手在左）
时收 `cross_hand = 0.2`。用户的口径：交叉比"多跑一段"更难受，
**宁可同手硬抗也不该交叉**。

它和 §4.3 是两件事：那条管的是**相邻两键挨得近**，这条管的是**两只手谁在左谁在右**。

> 0.2 是实测出来的：0 → 某些谱 35 处不同；**0.2 → 20 处且参考谱保持全对**；
> 0.3 → 30；0.5 → 31；0.7 → 21 但参考谱坏 2 处。快速交替段里两种分法总有一种
> 是交叉的，罚得太重会去翻相位。

### 4.5 动态偏好 `weight` 与"局部中心"的关系

`space.weight = 0.1`：按"偏离**局部中心**多少"增长，有 `neutral_band` 阈值
（0.03 坐标 ≈ **1/18 轨道**，小到几乎只在"键重叠"时才起作用）。

**但 `space.home` 是实际的主力。** 试过让"局部中心"（看前后约 1 秒邻居的
加权中心）主导，它在两个场景会把结果带偏：**扫动的折返极值点**（局部中心刚好
停在那个位置，位置证据归零，结果被物理项推向反手交叉）和**单侧 trill**。

所以现在只用最稳的组合：静态 `home` 管"在哪半屏"，动态 `weight` 管"偏离这一段
整体多少"。叠加后"左边给左手"在最左边最坚决、过中心线后翻转 ——
一条慢扫会被干净地切成"左半段左手、右半段右手"，而不是在中间来回换手。

**两个强度都刻意压得很轻。** 目标是*理想拆分*而不是"迁就手位"：
位置只是一条偏好，只要物理上两边都可行，"左手按右边的键、右手按左边的键"
是可以允许维持的（交叉手位在音游里很常见），不该压过节奏判断。

### 4.6 出张扣分 `reach`（默认关闭）

左手落到右半边 / 右手落到左半边时给一笔中等扣分，但**只在间隔 ≥100ms
（150 BPM 的16分）时收**：
时间足够时手完全来得及摆到正确的一侧，出张没有理由。
间隔很短时不收（快速交互里两手本来就必须来回跨）。默认 `0` = 关闭。

## 5. 手指停在"尾巴"位置 —— 长条与音弧

长条和音弧都不是"点一下"，而是**按住不放**：手从 `t1` 一路跟到 `t2`，
**结束那一刻停在尾巴的位置** `(x2, y2)`。这条语义影响三件事：

1. **移动距离的起点**：上一个物件是长条/音弧、下一个物件在它结束之后时，
   位移要从**尾巴**算起，而不是从上一个物件自己的位置算起；
2. **可用时间**：按住期间手被钉住，能用来移动的只有 `t2` 到下一个物件那一段。
   实谱里最夸张的一处是"扛着音弧 12 秒、弧尾到下一个键只剩 175ms
   （172 BPM 的8分）却要横跨 1.57 轨道 + 满高" ——
   不算尾巴的话会被当成"12 秒随便走"，完全不算账；
3. **尾指同手**：尾巴那一刻、**同一个点上**的判定物件必须同手
   （手指本来就在那儿；换手等于先弹开再弹回来）。

**"同一个点"是整个点，不是只比 x。** 地面长条尾指停在 `(x, 0)`，
正上方 `(x, 1)` 的天空键差**整整一个满高**—— 一根手指不可能同时按住地面
又点天空，必须换手。只比 x 会把这类键误判成"同一根手指能同时按下"，
进而产生假代价。

**占手的两侧处理不同**：

- **权重侧**（`hold_duration`）：`hold_min_duration = 260ms`（**115 BPM 的8分**），
  太短的长条不算占手（100ms = 150 BPM 的16分 那种短长条是 no-op）。
  `hold_tail_relax = 0`，即一直算到真结束。
- **硬约束侧**（`_hold_spans`）：长条区间内其它键必须换手（异色原则），
  始终用**真实区间**，不受权重侧松动影响。

如果手还按在长条上、下一个键就落在按住期间，这一下**不做位移速度判定**
（否则 `travel_time = 0` 会让速度项炸成天文数字），而是统一由 `busy`
（`hold_conflict_cost`）按"手被占住"收一笔平罚 20.0。

> **移动代价有封顶 `_MOVE_COST_MAX = 40`。** `travel_time` 趋近 0 时速度项会
> 平方级炸开（实测能到 25 万，把整份谱的判断全压掉）。再离谱也只是"这一下做不到"，
> 不该让它主导全局排序。

## 6. 硬约束 —— 走可行域，不是扣分

物理上做不到的事情**直接回绝**，不靠加大罚分。罚得再重，总会在某个局部上下文里
显得"划算"，于是输出里就会出现同色双押。

| 规则 | 处理 |
| --- | --- |
| **一键一手** | 同一时刻一只手只能按一个键 → 双押**必须一左一右**，同手分配根本不生成 |
| **原生 `side=`** | 最高优先级，绝不改动 |
| **arc 自身的颜色** | 不可修改（程序只读） |
| **同刻同点** | 地面物件与实体弧同刻起步**且落点相同** → 必须与弧同手 |
| **同刻不同点** | 不算"同一次落指"（那根手指正在起弧）→ 落到"区间异手" |
| **区间异手** | 地面物件落在实体弧区间内 → 不得使用弧的那只手 |
| **长条尾指同手** | 长条结束那一刻、同一位置的键必须同手 |
| **多押例外** | 同刻多押落在不同颜色弧内 → 两条规则打架，放行并记账 |
| **黑线**（`arctype=true`） | 没有颜色语义，不产生任何约束 |
| **挂黑线上的 Arctap** | 独立判定物件，和 tap/hold 一样要标手 |

**"同刻同手"必须带位置判据。** 实谱里 33 处"同刻起弧"的键**全部**相距 2 轨道以上
（最远 4 轨道）—— 只看时间不看位置，等于把根本不在同一处的键钉到同一只手上，
其中一处让左手同时被要求待在 x=0 和 x=1。

### 三押及以上

同一时刻 3 个及以上的键，触点数是 **≥ 3**，于是**必然**被 §7 的多指规则接管
（`multi_finger_min = 3`）：那一段的手标记直接按空间定死，
"一只手可以有几根手指"是常态，同刻两个键给同一只手不算错误。

所以实际输出是这样的（3 个同刻键，按 x 顺序分左右两半）：

```
(0,1) (0,2) (0,3)  →  L L R
(0,1) (0,2) (0,3) (0,4)  →  L L R R
```

> 只有在**非**多指配置下才会走"两只手按不下三个键"的退化分支
> （挑同手那一对跨度最小的分法）。这条路径对普通和弦形输入基本不可达，
> 但多指配置之外仍有触发的可能，所以保留着。

## 7. 多指配置：一只手可以有几根手指

同一时刻需要的**触点**数达到 `multi_finger_min = 3` 时，那一刻是一个
"多指配置"（典型写法：`2 长条 + 1 天键` / `1 长条 + 1 弧 + 2 tap`），
规则按用户口径收紧为**只看空间**：

- **需求手指数按触点算**：该时刻的判定物件 + 仍在按住/跟住的长条与实体弧
  （**弧头、弧尾都算**），但落在**同一个点**的只算一根手指
  （"键压在弧头上""上一条弧的尾巴正好接下一条弧的头"都是一根手指顺下去的事）；
- **±2ms 内的键并成同一个"时刻"**：谱面里常写 1ms 的错位和弦，
  玩家是按一个和弦打的，左右要一起分；
  （这两个数是**取整容差**、不是音乐间隔，换算成 BPM 没有意义；
  它们对应的是"玩家听起来是同时按下去的"同一个和弦。）
- **手标记直接定死**：每个物件先按绝对左右（`x < 0.5` → 左）；
  同一个 `y` 上有多个触点时按 x 从左到右分成左右两半
  （**实体弧的采样点也在这个排序里**）；**不同键之间的前后关系一概不看**；
- **骑在实体弧采样点上的键听弧色**：没有左右可排时，弧色是唯一信息；
  有左右可排时，弧的采样点只负责占位，拍板的是 x 顺序；
- **同一只手的多条弧只算一个触点**：否则两条同色弧会被数成两根手指，
  把普通配置误抬成多指段；
- **黑线不参与**：它的 `color` 没有语义，挂在它上面的天键本来就会被正常流程
  算一遍，再拿黑线的颜色去"锚"一次就是重复计算。

多指段里的键**豁免**长条相关的软约束（`busy`、长条头尾不能同色、区间异手），
只守**一键一手 / 原生标记 / 音弧颜色**这些最基本的。

钉手是**强偏好而不是硬约束**：与原生 `side=` 或音弧颜色冲突时听硬约束的。
兜底顺序是"原生标记 → 多指钉手 → 绝对左右"，并在 `warnings` 里显式报告。

## 8. 求解：束搜索 + 局部优化

```
按时间顺序扫过所有同时刻组
  每个状态记住：每只手最近按过的键、占手到什么时候、两手计数
  每组展开所有合法分配 → 按代价保留最好的 beam_width = 56 个
  同一个 key 只留最优状态（束宽可控的关键剪枝）
最后取总代价 + 均衡项最小的那个
然后局部优化：单键翻转 / 同标记交换 / 邻近交换 / 前缀翻转 / 整段镜像
```

**前瞻**来自束搜索本身：状态里存着"每只手最近按过的键"，
所以决定第 i 个键时已经知道前面的手位。

**全局**来自局部优化的**前缀翻转**（把某一段之后的标记整体左右互换），
它能修掉"这一段从哪只手起"选错的问题。

局部优化每轮把邻域**全部**评一遍、取最好的接受（steepest descent），
而不是"发现更好就立刻接受"—— 后者在"每 100ms（150 BPM 的16分）挪 0.1 坐标"
这类平坦但需要整体
协调的段落上会卡在次优解。

**均衡项**：左右手使用量相对偏差的 1.5 次方。差一两个键几乎不罚，
差一半以上才明显罚 —— 既要"别偏科"，又不能"为了凑平衡把该抗的一串键硬拆开"。

## 9. 调参建议

**只有两个旋钮**，其余全部按 Arcaea 实测固化（想改它们等于改模型，不是调参）。

| 参数 | 默认 | 调大的效果 |
| --- | --- | --- |
| `cost.jack` | 4.0 | 更愿意拆交互、更不愿同手连打 |
| `cost.move` | 1.0 | 手更"偷懒"、更倾向就近按键 |

```bash
# 扫一个权重，对比不同取值下的分法
for j in 3 4 5 6; do
  python3 spliter_aff.py 谱面.aff --jack $j -o /tmp/j$j.aff
done

# 与人工参考逐处对照（含"把该簇整簇改成参考答案要多少代价"）
python3 tools/diff_report.py 谱面.aff 参考.aff
```

`diff_report.py` 那一列"**本簇翻成你的代价**"是关键：接近 0 说明两种分法在模型里
**等价**（平局，不是错），明显为正才是真分歧。只翻单个键会误导 ——
这些差异常常是"一整段交替的相位反了"，必须**按簇**（相邻 400ms = 75 BPM 的8分
以内算同一簇）一起翻。

### 什么时候该怀疑参数

- **该交替的地方在硬抗**：调大 `cost.jack` 或 `cost.hardness`。
- **每下都换手、看着累**：调小 `cost.jack`，或看 `switch` 是否在压过物理。
- **手在乱跑**：调大 `cost.move`。

## 11. 已知边界

- **多押（同刻 3 个及以上）**：触点 ≥3 会被 §7 的多指规则接管，按空间定死，
  一只手可以拿到相邻的两个键；**不会**出现"三个键全给一只手、另一个空着"，
  也不会出现空标记。
- **性能**：瓶颈在局部优化。要更快就调小 `search.refine_passes` /
  `refine_radius`，或关 `refine_mirror`。
